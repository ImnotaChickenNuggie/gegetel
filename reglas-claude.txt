  comandos siempre utilizarán pnpm, los componentes globales o compartidos      
  vivirán en una carpeta global de next.js. Todo el desarrollo frontend estara  
  basado en las versiones LTS de next.js para mantener actualizado el sistema,  
  si detectas en package.json que la versión actual no es LTS deberás indicarlo 
  al usuario para su actualización. El manejo de estilos y componentes se       
  realiza con tailwindCSS y Shadcn, iconografía con lucide-react, nunca debes   
  ejecutar nuevos diseños o propuestas que estén fuera del diseño generado,     
  eres el encargado de codificar, no de diseñar la UX/UI, puedes enviar         
  sugerencias que aprobará o no el usuario. Si necesitas componentes de Shadcn  
  utiliza el comando: pnpm --filter <target-package> dlx shadcn@latest add      
  <component_name>. El codigo typescript es estricto con interfaces claras para 
  las props, las variantes se definen mediante cva (class-variance-authority)   
  y la combinación de clases con cn. Maneja el desarrollo con clean code,       
  accesible y modular, listo para escalar.

        <component_name>; revisar src/components/ui antes; no modificar

     5. Arquitectura hexagonal:
     src/
       app/                      # rutas Next = adaptador primario (solo 
     composición)
         providers.tsx           # QueryClientProvider
       modules/<feature>/
         domain/                 # entidades, value objects, puertos. TS puro
         application/            # casos de uso; dependen solo de domain
         infrastructure/         # adaptadores http/API, mappers DTO↔dominio
         ui/                     # componentes + hooks del feature
           hooks/                # useQuery/useMutation que invocan casos de uso
         <feature>.keys.ts       # query keys del módulo
         <feature>.container.ts  # composition root
         index.ts                # API pública del módulo
       components/ui/            # primitivos shadcn
       components/shared/        # componentes globales/compartidos
       hooks/  lib/
        Reglas: dependencias hacia dentro (ui→application→domain; infrastructure
        implementa puertos). domain/application sin React, Next, TanStack,
        fetch. UI no llama API directo: hooks TanStack ejecutan casos de uso en
        queryFn/mutationFn. Query keys centralizadas por módulo; invalidaciones
        vía keys. DTOs nunca cruzan a domain. Sin imports a internos de otros
        módulos (solo index.ts).
     6. Estilos: Tailwind v4 + tokens globals.css; sin CSS ad-hoc ni colores
        hardcoded. Iconos solo lucide-react.
     7. TypeScript strict: sin any; interface <Nombre>Props exportada; extender
        React.ComponentProps<"el"> + VariantProps<typeof xVariants>.
     8. Variantes/clases: cva para variantes; combinar clases con mergeClasses
        de @/lib/utils (cn reservado, no usar). Si mergeClasses no existe →
        avisar al usuario antes de crearlo. Ejemplo corto del patrón.
     9. Clean code: componentes pequeños, single-responsibility, Server
        Components por defecto, "use client" solo si necesario (hooks TanStack ⇒

  Reglas de Ejecución y Monorepo                                                
                                                                                
  1. Comandos de Package Manager: Usa SIEMPRE pnpm con scope.                   
     - Ejemplo: pnpm --filter <app-name-or-package> add <package> o pnpm        
  --filter <app-name> run test.

  packages/backend-core).                                                       
                                                                                
  Arquitectura Hexagonal (Estructura de Capas)                                  
                                                                                
  Cada módulo debe mantener la separación en tres capas claras:                 
                                                                                
  1. Domain (Núcleo Central - Sin Dependencias de NestJS ni Prisma):            
     - Entities: Objetos de dominio puros en TypeScript.                        
     - Ports: Interfaces que definen los contratos para repositorios, servicios 
  externos y eventos (outbound ports) o casos de uso (inbound ports).           
     - Exceptions: Excepciones nativas del dominio.                             
  2. Application (Casos de Uso):                                                
     - Use Cases / Services: Implementación de la lógica de negocio consumiendo 
  únicamente Puertos (interfaces).                                              
     - DTOs internos y mapeadores de comandos.                                  
  3. Infrastructure (Adaptadores Externos):                                     
     - Persistence: Implementaciones de repositorios con Prisma ORM             
  (PrismaService, mappers de modelo Prisma a Entidad de Dominio).               
     - Webhooks: Drivers y handlers para la recepción/procesamiento de webhooks 
  (ej. Stripe, automatizaciones, integraciones de terceros). Deben incluir      
  verificación de firmas de seguridad, idempotencia y mapeo a DTOs/Casos de     
  uso.                                                                          
     - Entry Points (HTTP / Controllers): Controladores de NestJS               
  (@Controller), validadores de entrada con class-validator / class-transformer 
  y Swagger (@nestjs/swagger).                                                  
                                                                                
  Reglas para Prisma ORM                                                        
                                                                                
  - Prisma es un detalle de infraestructura. Las entidades de dominio NUNCA     
  importan tipos generados por @prisma/client.                                  
  - Define siempre un Mapper en la capa de infraestructura para convertir de    
  Prisma Model -> Domain Entity y viceversa.                                    
  - Maneja transacciones en la capa de persistencia mediante repositorios o     
  patrones Unit of Work.                                                        
                                                                                
  Manejo de Webhooks                                                            
                                                                                
  - Al construir o actualizar endpoints de Webhooks:                            
    1. Verifica siempre las firmas o tokens de seguridad en la capa de entrada  
  (Guards/Middlewares).                                                         
    2. Implementa validación de idempotencia (usando Redis o DB) antes de       
  ejecutar el caso de uso.                                                      
    3. Responde rápidamente con 200 OK delegando procesamientos pesados a colas 
  o eventos asíncronos si aplica.                                               
                                                                                
  Inyección de Dependencias en NestJS                                           
                                                                                
  - En los módulos de NestJS (@Module), vincula los Puertos (Interfaces) con    
  las Implementaciones de Infraestructura usando Tokens/Providers
